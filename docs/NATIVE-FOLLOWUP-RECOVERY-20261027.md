# 桌面追问的自动确认与恢复

普通发送与排队发送会先保存原任务、完整正文、附件引用、模型选项和请求编号，再交给主进程。回复丢失或超时后会自动核对原编号；切换任务、重载界面，或再次打开应用后，仍沿用原请求恢复，无需点击继续。每个任务同时保留一条待确认消息，期间可继续编辑新草稿。

待确认记录绑定应用数据目录的持久身份。另一套数据不会接收旧环境的请求；后台列表可查看原任务和恢复状态，并停止对该记录的确认。身份文件读取失败不重置身份、不阻止其他界面启动；读取恢复后会自动重试。

## 接受回执与停止操作

主进程使用调度器保存的消息回执去重。确认一条已经接受的消息，不会再次入队，也不会撤销后来的暂停或取消。尚未接受的旧请求会在串行投递位置检查控制版本，不能跨过后来发生的停止操作。

“停止确认并保留草稿”会先与主进程中正在进行的同编号投递汇合。消息已接受时返回原接受结果；尚未接受时保存取消记录，以阻止重载或重启后的再次投递。取消记录只保存编号和输入摘要。停止确认不召回已经接受的消息；若要停止执行，可使用任务的暂停/取消操作。

## 草稿保留

成功确认只清理原消息拥有的文本和附件引用；后来输入的其他文本、其他任务的草稿及新附件会保留。草稿清理与确认编号一起保存，然后才移除待确认请求。即使最后清理请求的存储操作失败，重试也不会再次清掉后来输入的新草稿，包括与原文恰好相同的新文本。

存储失败时不发送未保存的新请求。持久记录读取失败时保留原记录；当前容量最多 100 条，存储失败会保留草稿。后台以两个工作槽恢复，失败后逐步退避至最多 60 秒。普通追问使用可靠排队入口；立即补充到当前轮次仍是需要当前工作进程的即时操作，不自动重放。[新聊天创建使用独立可靠入口](NATIVE-CREATION-RECOVERY-20261027.md)。

## 验证

Node 集成覆盖完整调度器/状态重启、安装身份、重复输入编号、暂停之后的接受回执、取消落盘后确认丢失及取消与接受的并发顺序。渲染器检查覆盖存储失败、超时、重载、损坏或不可重放的记录、清理确认失败及新草稿保留。

`scripts/qa/native-followup-ui.cjs` 使用生产桌面界面和模拟 IPC，验证四语言、150% 缩放、启动 IPC 暂时失败、丢失回复后跨任务重载、取消及后续暂停。它不代表已在原生 Windows 安装器中执行，也不发送真实模型请求。
