# Telegram 手机控制台：实现与验证（2026-10-23）

本次围绕服务器 Telegram 的完整使用流程交付一个功能升级，不按小修补凑迭代轮数。配置和启用方式见 [Telegram 使用指南](TELEGRAM.md)。

## 使用上的变化

- **项目和任务导航**：`/start` 打开按钮面板，项目每页 10 项、任务每页 8 项。保存当前项目、任务和新任务默认值；新建后直接文字追问，回复已知任务卡片可指定投递对象。
- **结果交付**：最新回答、历史、搜索结果和完整排队文字可翻页；页面固定为内容快照，避免流式更新造成翻页错位。对话 Markdown、任务诊断 JSON、工作流交接 Markdown 可通过 Telegram 文件下载。
- **工作流和模板**：一条消息创建 2–12 阶段依赖链；使用已保存模板，调整新任务的模型、推理强度和计划模式。工作流创建具备持久化去重。
- **任务和调度管理**：编辑、删除、调整排队消息顺序；设置优先级、名称、置顶、归档与依赖；暂停/恢复项目或全局派发，设置项目并发上限。
- **审批与提问**：完整请求逐条浏览；命令/权限请求显式同意或拒绝；结构化提问逐题点选或文字回答，回答全部问题后提交。旧按钮、请求变更、重复选择和重启后的旧授权不会继续执行。
- **主动通知**：完成时给结果摘要和操作按钮；自动恢复时说明正在处理、无需点击继续；批量通知分批发送并保留未发送项，不再静默丢弃超出首批的任务。

## 重试和持久化

`telegram-state.json` 保留解析后的入站命令、项目/任务/默认值快照、完整出站回复/文件和最近 200 条任务消息映射。既有版本 1 状态可继续读取，新增字段均为可选字段。

入站记录落盘前不执行操作。`/run` 的项目序号先解析成实际目录再保存，因此重启后调整工作目录配置顺序也不会改变投递位置。任务、工作流、追问沿用调度器的确定性请求 ID 和持久化回执。

出站确认丢失时 Telegram 文本或文件可能重复出现；任务/工作流创建和追问不会因此重复。队列版本检查阻止旧操作覆盖新内容；审批和按钮控制采用一次性短时凭据，结果不确定时要求重新查看。答题模式在重启后保留“这是答案”的边界，不会把回答误发成任务指令。

另修正一项已有 Git 并发测试：并行调用在进入队列前需要异步解析目录，两个调用可能任意一个先到。测试现在要求恰好一次提交成功、另一次因版本变化失败，同时核实获胜提交的标题与文件内容，不再错误要求第一个调用必胜。

## 验证边界

本次没有配置用户的真实 Telegram Bot、发送真实 Telegram 消息或调用模型；Telegram HTTP 表单编码通过模拟 fetch 检查。没有声称真实 Bot 网络、Telegram 客户端显示或生产部署已验收。

Telegram 桥接运行于 Linux 服务端。Windows/手机可通过 Telegram 客户端使用该服务；本次未进行原生 Windows 实机验收，也未替换已发布 Windows 安装包。

尚未实现语音转写、上传二进制附件、任意项目文件下载、通过 Telegram 导入账户密钥或管理服务器生命周期。长内容、通知数量、授权和分页有效期等限制在使用指南中明确列出。
